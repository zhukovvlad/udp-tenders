# Видимость счетов без распознанного направления — Design

**Дата:** 2026-06-16
**Статус:** согласовано (brainstorming), готов к writing-plans

## Проблема

В мульти-направленном объекте (есть бетон + арматура) распознанные счета-фактуры, не попавшие ни в одно направление, **исчезают из поля зрения**.

Воспроизведение: загружается УПД, где материал — не бетон и не арматура (напр. «Прокат чёрных металлов», `material_class=null`, `material_type="other"`). Парсинг проходит успешно (`status="parsed"`, не error). Но счёт не виден нигде:

- **«Все направления»** (вид по умолчанию мульти-объекта) — это сводка: KPI + график отклонений + алерт нераспознанных. **Таблицы счетов в ней нет вообще.**
- **Вкладка «Счета»** появляется только при выборе конкретного направления, и `/dashboard/invoices?direction=concrete` отдаёт лишь счета с ≥1 material-позицией этого направления. «Прочий» счёт не попадает ни в бетон, ни в арматуру.
- **`other` не является направлением** (ADR #9), отдельной вкладки «Прочее» нет.
- **«Ошибки»** его не показывают — он не ошибка.

Итог: счёт учитывается лишь числом в KPI «Счетов → Прочие · N», но открыть/увидеть сам счёт негде.

## Решение (исход: видимость; классификацию не меняем)

Дать «Все направления» полноценный список всех счетов объекта + клиентский фильтр «только прочие». Это закрывает баг буквально: «Все» становятся *всеми*.

Размещение и UI — чистый фронт (данные уже загружены). Определение «прочий» — через бэкенд (единый источник истины классификации направления, см. ниже).

### Ключевое архитектурное решение: предикат «прочий» — поле от бэкенда (2b), не клиентская реконструкция (2a)

**Отвергнутый вариант 2a** (клиентский предикат через матч по имени класса): завёл бы **второй источник истины** о направлении. Сегодня единственный — БД: `material_class.material_type_id → material_types`, матч по id, та же логика, что кормит summary, графики, коридоры, экспорт. Имя класса — мутабельная человекоредактируемая строка (`get_or_create_material_class` создаёт по имени, в Review правят). Клиентский матч по имени молча разойдётся с бэкендом при переименовании/новом классе, и — хуже — рассинхрон станет ненаблюдаемым: фронт согласован сам с собой, но таблица счетов и график отклонений разойдутся в том, какой счёт «прочий».

**Принятый вариант 2b:** бэкенд возвращает на каждый счёт `directions: string[]` (коды направлений, которых счёт касается; `[]` = прочий), матч по id, **тем же резолвером**, что наполняет `directions[]` в summary. Клиентский предикат вырождается в `inv.directions.length === 0` — нечему дрейфовать. Это **не** `?direction=other`-фильтр: `other` не становится направлением, мы лишь описываем, каких направлений касается счёт — ADR #9 цел.

Критерий выбора: «без бэкенда» — ограничение на UI-работу (размещение, пункты ниже — там бэкенд не нужен), **а не лицензия дублировать доменную классификацию на клиент**. Единый источник истины классификации весомее экономии пяти строк.

## Backend

### Шаг 1: извлечь общий резолвер направлений по счёту

Сейчас «какие направления у счёта» считается инлайн в `_direction_summaries` (`routers/dashboard.py`, блок `inv_type_rows` → `types_by_invoice`, ~строки 82–98): join `Invoice → InvoiceItem → MaterialClass`, фильтр `item_type='material'` + `material_type_id IN direction_type_ids` (≠ other), `distinct`.

Извлечь в общий хелпер (единственная реализация):

```python
def _directions_by_invoice(db, project_id, excl_filter=lambda q: q) -> dict[int, set[str]]:
    """Коды направлений (material_types, кроме other; ADR #9), которых касается каждый счёт.
    Единый резолвер — матч по material_class.material_type_id, item_type='material', distinct.
    Используется и summary (§5.5), и /dashboard/invoices. excl_filter — опционально, для summary."""
```

Возвращает коды (не id): для summary это эквивалентно (`t.code in s`, `len(s) >= 2` для mixed), для эндпоинта — готовый список.

- `_direction_summaries` переключается на этот хелпер (передаёт свой `_excl_filter`); его внутренняя логика поведенчески не меняется (`t.id in s` → `t.code in s`, mixed-детект по длине code-set). Покрыто существующими dashboard-тестами.
- Инвариант: это **тот же** резолвер, не вторая ветка. Если в сериализаторе появится отдельная реализация «какие направления у счёта» — вернётся проблема двух источников, просто оба на бэке.

### Шаг 2: добавить `directions` в payload `/dashboard/invoices`

В `list_project_invoices` посчитать `dir_map = _directions_by_invoice(db, project_id)` (без excl-фильтра — это сырой список всех счетов объекта) и добавить в каждый счёт:

```python
"directions": sorted(dir_map.get(inv.id, set())),   # [] = прочий
```

Поле описательное, не влияет на существующий `?direction=` фильтр эндпоинта.

## Frontend

### Тип

`DashboardInvoiceRow` (`types/invoice.ts`): добавить `directions: string[]`.

### Размещение списка (пункт согласован — секция, не мини-табы)

В `AllDirectionsSummaryView` (`ProjectPage.tsx`) после графика отклонений добавить секцию **«Счета · N»** с готовым `<InvoiceTable invoices={...} />`. У `InvoiceTable` свои поиск/пагинация/фасеты — скролл ограничен. Мини-табы «Сводка | Счета» не вводим: дробят то, что читается одним скроллом, и плодят навигационное состояние.

`invoices` в режиме «Все» уже = полный список (в этом режиме `scopedDirection === undefined` → `/dashboard/invoices` без фильтра → все счета; запрос уже выполняется). `InvoiceTable` не меняем по сигнатуре — фильтрацию делаем на уровне страницы, передавая отфильтрованный массив.

### Фильтр «Прочие» (клиентский, над уже загруженным массивом)

- Page-level состояние `showOnlyOther: boolean`.
- В `InvoiceTable` передаём `showOnlyOther ? invoices.filter(i => i.directions.length === 0) : invoices`.
- **Источник счётчика и фильтра — один и тот же клиентский массив `invoices`.** Кликабельная строка «Прочие · N» в KPI-карточке «Счетов» показывает `invoices.filter(i => i.directions.length === 0).length` и по клику ставит `showOnlyOther=true` + скроллит к таблице. Сброс — видимый «× все счета».
- Это гарантирует «бейдж N == строк после фильтра» тавтологически (одна и та же функция над одним массивом), независимо от исключённых поставщиков.
- **Тонкость с исключёнными поставщиками:** существующий `summary.other_invoice_count` считается с excl-фильтром (исключённые поставщики выкинуты), а `/dashboard/invoices` отдаёт все счета. Поэтому кликабельный счётчик «Прочие» берём из клиентского массива (`invoices`), **не** из `summary.other_invoice_count` — тогда клик→результат всегда совпадают. Это согласуется с тем, как исключения работают везде: KPI-математика их выкидывает, сырой список счетов — показывает все.

### Метка сирот и null-колонки

- Колонка «Позиции» уже рисует `material_class || item_type` — для `other`-позиции покажет `other` (не пусто). Оставляем, но `other` визуально мягко (как сейчас `text-fg-tertiary`).
- Для строк-сирот (`inv.directions.length === 0`) — мягкий бейдж **«прочее»** рядом с номером (по аналогии с `border-danger` для review). `InvoiceTable` читает `inv.directions` напрямую (поле уже на строке) — доп. проп не нужен. Семантику не трогаем.

## Тесты

- **Backend unit** (`_directions_by_invoice`): моно-бетон / моно-арматура / смешанный (оба кода) / чисто-other / без позиций / только-доставка → корректные коды или `[]`.
- **Backend**: `/dashboard/invoices` возвращает `directions` на каждом счёте; смешанный → оба кода; прочий → `[]`. Регрессия summary: dashboard-тесты направлений зелёные после рефактора (поведение `_direction_summaries` не изменилось).
- **Frontend компонент** (`ProjectPage`): в «Все направления» рендерится таблица со всеми счетами; клик «Прочие · N» сужает список; число в бейдже == числу строк после фильтра (страж рассинхрона); строка-сирота несёт бейдж «прочее».

## Вне скоупа (YAGNI)

- Авто-классификация при загрузке, новые направления/классы, ручное назначение класса в Review.
- Изменение бэкенд-инвариантов (`other` не направление — остаётся).
- Сегмент «Прочее» в `DirectionSwitcher` (потребовал бы `?direction=other` → 422 / нарушение ADR #9 — отвергнут).
