# Контракт окружения: роль вместо вендора

**Дата:** 2026-07-27
**Статус:** дизайн согласован, реализация в ветке `feat/local-dev-db` (PR #45, черновик)
**Базовая ревизия:** `7edca85` — вводит guard с вендорной осью, эта спека его перерабатывает **до мержа**; `main` вендорную ось не видит никогда.

---

## 1. Проблема

25.07.2026 на дев-машину раскатали корпоративную TLS-инспекцию (CA `Generic Root CA 3`).
`channel_binding=require` в DSN честно детектирует подмену сертификата, и все коннекты к
Neon падают с `insecure connection: secure channel data mismatch`. Дев-цикл переехал на
локальную БД `udp_dev` (ревизия `7edca85`), и вместе с переездом появился guard от
случайной записи в развёрнутую БД.

**Guard был построен по неверной оси — вендору.** Он ключуется на домен `neon.tech`, тогда
как прод не обязательно Neon: развёртывание возможно и на сервере компании (LLM через
gateway, БД локальная или в докере), и на стороннем хостинге. Следствия:

- **хостинг в компании** — `is_neon_url()` вернёт `False`, guard молчит, у настоящей
  прод-БД защиты нет вовсе;
- **сторонний хостинг с Neon** — guard блокирует легитимный старт прода, пока не выставят
  `ALLOW_NEON_WRITES=1`, то есть конфигурация прода зависит от того, кто хостит его базу;
- guard не различает прод-Neon и test-ветку Neon — именно поэтому в `7edca85` понадобились
  три разных escape hatch.

Вторая проблема, вскрытая тем же переездом: `backend/.env.example` подаёт Neon-DSN как
**единственный** вариант `DATABASE_URL`. Это и есть исходная ложная привязка, из которой
выросла вендорная ось.

## 2. Решение в одном абзаце

Guard переключается с вендора на **роль окружения**: новая переменная `APP_ENV` (`dev` |
`prod`, дефолт `dev`) и allowlist целей `DB_EXTRA_TARGETS` для dev. `ALLOW_NEON_WRITES`
удаляется. Профили развёртывания остаются **рецептами эксплуатации**, а не сущностями в
коде: LLM-провайдер уже переключается существующим `LLM_PROVIDER`, цель БД — `DATABASE_URL`,
роль — `APP_ENV`. Спека добавляет **две переменные** (`APP_ENV`, `DB_EXTRA_TARGETS`), один
рефактор модуля и честные доки. Новых сущностей — ноль.

## 3. Отклонённые варианты

Перечислены, чтобы промежуточные итерации не всплыли в реализации как «а вот же было».

| Вариант | Почему отклонён |
|---|---|
| `ALLOW_NEON_WRITES` + `is_neon_url()` (реализовано в `7edca85`) | вендор в контракте: не защищает on-prem, ломает прод на Neon, не различает прод и test-ветку. Плюс разрешение было **рантайм-мутацией** process env из фикстуры, а не конфигом |
| `DEPLOY_PROFILE=company\|external` — один энум, выводящий дефолты LLM и БД | склеивает две технически независимые оси: гейтвей компании не мешает подключить Neon, сторонний хост не мешает поднять Postgres в докере. В коде уже выбран независимый путь (`LLM_PROVIDER`) |
| Файлы-пресеты `.env.onprem.example` / `.env.external.example` | имена смешивали обе оси; «БД по обстоятельствам» — признак того, что БД в профиль не входит |
| Файлы-пресеты `.env.gateway.example` / `.env.openrouter.example` | **отложено до фазы 2.** `.env.example` уже содержит `LLM_PROVIDER=openrouter` и весь openrouter-namespace — второй файл был бы почти побайтовым дублем. Gateway-пресет невозможен: auth-блок не финализирован до Keycloak-спайка, контракта ещё нет. Указатель на фазу 2 уже стоит комментарием `# GATEWAY_BASE_URL=` в базовом примере |
| `DB_ALLOWED_TARGETS` как имя | обещает полный список, а механизм — добавка к неявному loopback. Имя не должно скрывать факт |
| `DEV_DB_EXTRA_TARGETS` / `DB_DEV_EXTRA_TARGETS` | не проходит форму 3 контракта имён (нет базовой `DB_EXTRA_TARGETS`, которую оно переопределяло бы); «только в dev» — свойство механизма, а не переменной |
| Денилист защищённых хостов (`PROTECTED_DB_HOSTS`) | защита появляется только там, где список не забыли пополнить; забыл хост — узнаёшь по факту аварии |
| Убрать guard, оставив дефолт `db_target=local` в justfile | возвращает дыру: команда мимо `just` снова уходит в развёрнутую базу. Это самый вероятный путь на практике |
| Guard внутри `database.py` при создании движка | модуль импортируется на этапе сбора тестов, до того как окружение готово |

## 4. Контракт имён

### Три формы

| Форма | Где применяется | Носители сегодня |
|---|---|---|
| `<ДОМЕН>_<ЧТО>` | конфиг приложения (`backend/.env`) | `LLM_PROVIDER`, `OPENROUTER_*`, `GATEWAY_*`, `S3_*`, `COOKIE_*`, `APP_ENV`, `DB_EXTRA_TARGETS` |
| `UDP_<ДОМЕН>_<ЧТО>` | переменные инструментов уровня машины | `UDP_DB_TARGET` (общий шелл, рядом ещё четыре проекта) |
| `<ENV>_<ДОМЕН>_<ЧТО>` | переопределяет **одноимённую базовую** переменную для конкретного окружения | `TEST_DATABASE_URL` (переопределяет `DATABASE_URL`) |

Форма 3 определена узко — «переопределяет одноимённую базовую». Это сознательно: широкое
определение («скоуплено на окружение») впустило бы в правило контрпримеры.

Канонический токен домена БД — **`DB`**. `DATABASE_URL` — замороженное исключение,
прецедентом написания не является.

**Файлы:** `.env.<scope>.example`, рядом с той копией, которую из него делают. Проверено:
`backend/.env.example` → `backend/.env`; корневой `.env.test.example` → корневой `.env.test`
(его и потребляет pytest-dotenv — `find_dotenv(usecwd=True)` поднимается от CWD=`backend/`
вверх). Расхождения нет.

### Четыре корзины

| Корзина | Переменные | Критерий выхода |
|---|---|---|
| Соответствуют | `LLM_PROVIDER`, `OPENROUTER_*`, `GATEWAY_*`, `S3_*`, `COOKIE_*`, `ACCESS_TOKEN_EXPIRE_MINUTES`, `REFRESH_TOKEN_EXPIRE_DAYS`, `TEST_DATABASE_URL` | — |
| Замороженные исключения | `DATABASE_URL`, `SECRET_KEY`, `LOG_LEVEL` | не переименовываются никогда. Причина — внешние потребители: Alembic читает `DATABASE_URL` сам, CI подаёт его через process env, есть 12-factor-ожидания. **Не** «файл их скопил»: `Settings` объявлен без `env_prefix`, и process env имеет приоритет над `env_file` — CI это доказывает, подавая `DATABASE_URL`/`SECRET_KEY`/`OPENROUTER_API_KEY` вообще без файла `.env`. Риск подмены из общего шелла закрывает guard — это его второе оправдание помимо защиты от команд мимо `just` |
| Отклоняются, отложены | `CONFIDENCE_THRESHOLD`, `ALLOWED_ORIGINS`, `TRUSTED_PROXIES` | вне этой задачи, запись в `docs/TECH_DEBT.md`. `CONFIDENCE_THRESHOLD` не «завязан на Settings API» — он через `set_key` в него **записывается**, поэтому переименование требует миграции существующих `.env` |
| Legacy-алиасы | `AI_MODEL` | путь смерти есть (`unset_key` на PUT модели + warning) — не трогаем |
| | `AI_MAX_TOKENS` | **пути нет** — `resolved_openrouter_max_tokens` тернарником возвращает legacy без предупреждения. Добавить warning через `_warn_deprecated_alias_once` |
| | `PDF_ENGINE` | **пути нет** — условие `legacy != "mistral-ocr"` в `resolved_openrouter_pdf_engine` глушит warning ровно для значения из легаси-`.env`. Снять условие; см. AC-9 (неделимая сцепка) |

### Мёртвый конфиг

`TEST_MODE` удаляется из `.env.test.example` (и вручную из `.env.test`, см. §9).
Потребителей в коде ноль: `routers/test_utils.py` не существует, `main.py` флаг не читает,
единственная живая ссылка — `docs/testing.md`, раздел отложенного E2E.

**Важно для будущего исполнителя E2E-задачи:** план `2026-05-11-testing-infrastructure.md`
намеренно вводит `TEST_MODE` заново вместе с `/api/test/reset`. Удаление сейчас — YAGNI по
нереализованной фиче, **не** отклонение E2E-дизайна. Строку в `docs/testing.md` не трогаем:
как описание отложенного плана она корректна.

## 5. Механика guard'а

### Сигнатура и чтение конфига

```python
def ensure_mutation_allowed(url: str, action: str) -> None:
    """Прервать action, если цель не разрешена для текущего APP_ENV."""
```

Конфиг читается через свежий `Settings()`. Это даёт `Literal`-валидацию `APP_ENV`, один
путь чтения для всех call-site и независимость от CWD (после правки `env_file`, коммит 1).

Цель передаётся **аргументом** — тем URL, который вызывающий собирается мутировать, а не
`settings.DATABASE_URL`. Принципиально: в `db-test-migrate` цель приходит из process env,
в `conftest` — из `cfg.set_main_option("sqlalchemy.url", test_url)`, и глобальная настройка
их не описывает.

### Решение

| `APP_ENV` | Поведение |
|---|---|
| `prod` | цели не проверяются. Декларация роли **и есть** разрешение: цель прода — его `DATABASE_URL`, требовать вдобавок перечислить собственный DSN значило бы вторую обязательную переменную с нулевым приростом безопасности |
| `dev` (дефолт) | цель обязана быть в разрешённом множестве, иначе `RuntimeError` **до** коннекта |

Разрешённое множество в `dev` = неявный loopback (`localhost`, `127.0.0.1`, `::1` — любая
база) **плюс** нормализованные записи `DB_EXTRA_TARGETS`.

### Новые переменные

```dotenv
APP_ENV=dev|prod          # Literal, дефолт dev; невалидное значение падает на валидации
DB_EXTRA_TARGETS=         # список host:port/dbname через запятую, дефолт пустой
```

**Почему `DB_EXTRA_TARGETS` существует при нуле фактических потребителей** (после ревизии
§12 их ноль, докерных артефактов в репозитории нет — см. §11). Обоснование **не** Rule of
Two и не «пригодится в будущем»: по этой букве переменную снесло бы следующее YAGNI-ревью,
как оно правильно снесло файлы-пресеты. Обоснование — цена отсутствия. Guard построен на
deny-by-default; если у него нет **скоупленного** выхода, единственным выходом остаётся
**нескоупленный** — `APP_ENV=prod`. Тогда любой легитимный краевой случай (dev в
докер-компоузе, где приложение в контейнере тянется к БД по хосту `db`; общий дев-Postgres
на другой машине) конвертируется в полное отключение защиты на всей машине. Предохранительный
клапан оправдан ценой своего отсутствия, а не числом текущих пользователей — это другой класс
сущностей, чем дублирующий пресет.

`extra="ignore"` в `Settings` означает, что опечатка в **ключе** (`APP_ENVIRONMENT=prod`)
молча даёт дефолт `dev`. Это ограничивающий режим, поэтому отказ произойдёт громко — на
первой же мутации не-loopback цели. `extra` не меняем.

### Нормализация цели

Единица сравнения — `host:port/dbname`. Именно так, потому что CI различает свои две цели
**только именем БД**: `localhost:5432/postgres` против `localhost:5432/udp_test`.

- hostname из `urlsplit`, в нижнем регистре, без завершающей точки;
- порт — явный или `5432`;
- dbname — path без ведущего слэша;
- query-параметры отбрасываются (из-за них строковое равенство полных DSN в старой проверке
  `conftest` было дырявым);
- **пустой hostname** (socket-DSN, битый URL после отказа `urlsplit`) → цель не loopback и
  не матчится ни с чем, то есть в dev запрещена (fail-closed); в тексте ошибки показывается
  как `<нераспознанный хост>`, а не пустой строкой;
- нормализация применяется к обеим сторонам сравнения;
- каждая запись `DB_EXTRA_TARGETS` — **полная тройка**: запись без dbname (`host:port`) или без
  порта — ошибка валидации, а не «любая база на этом хосте». Иначе allowlist незаметно
  расширяется до уровня хоста, что противоречит выбору единицы сравнения;
- битая запись в `DB_EXTRA_TARGETS` — ошибка валидации на старте, не молчаливый пропуск.

### Три call-site

| Где | Что передаёт | Почему отдельно |
|---|---|---|
| `alembic/env.py` | `_db_url` после резолва `sqlalchemy.url` → process env | единственный путь, который видит цель из рецепта. `config` доступен транзитивно: `from database import Base`, а `database` делает `from config import settings` — синглтон инстанцируется на уровне модуля, то есть валидационное поведение в env.py уже есть сегодня. Новой связи не создаём |
| `cli.py` | `settings.DATABASE_URL` | до `SessionLocal()` — иначе «fail-fast» означает коннект и лишь потом отказ |
| `main.py::_sweep_stuck_documents` | `settings.DATABASE_URL`, только ветка `session_factory is None` | sweep пишет в БД на каждом старте, поэтому `uv run uvicorn main:app` вместо `just dev-backend` испортил бы живые прод-документы. Инжектированная фабрика (тесты) — заведомо тестовая цель, её не проверяем |

### Текст ошибки

Требования, не пожелания:

1. отвергнутая цель печатается **в нормализованной форме** — ровно той, которую принимает
   `DB_EXTRA_TARGETS`. Совпадение форматов фиксируется требованием, чтобы второй выход был
   copy-paste;
2. названы **оба** выхода — `APP_ENV=prod` для развёрнутого окружения и `DB_EXTRA_TARGETS`
   для дев-цели;
3. хост без креденшелов — строка уходит в логи и CI-вывод.

```
alembic: цель localhost:5432/other_db не разрешена при APP_ENV=dev.
Разрешено: loopback + DB_EXTRA_TARGETS (сейчас пусто).
Если это развёрнутое окружение — выставьте APP_ENV=prod.
Если это дев-цель — добавьте localhost:5432/other_db в DB_EXTRA_TARGETS в backend/.env.
```

### Инвариант единственного потребителя

У объявления `APP_ENV` в `config.py` — комментарий: **единственный потребитель `APP_ENV` —
`db_guard`; новый потребитель обязан пересмотреть деплойную таблицу, потому что loopback-прод
без явного `APP_ENV` останется в dev-режиме.** Без этого инварианта первый же будущий
потребитель (`COOKIE_SECURE` по env, debug-эндпоинты) превратит тихий dev-режим на
loopback-проде из безвредного в дыру.

### Инварианты `db-test-migrate`

Корректность рецепта висит на двух независимых деталях, обе фиксируются:

1. **`load_dotenv(ROOT / ".env")` в `alembic/env.py` вызывается с `override=False`** (дефолт
   python-dotenv). `backend/.env` содержит прод-DSN; сейчас process-env из рецепта
   побеждает. Станет `True` — рецепт начнёт мигрировать **прод**. Покрывается регрессионным
   тестом по исходнику (AC-7). Новый guard работает здесь вторым эшелоном: при перевёрнутом
   `override` цель станет прод-DSN, которого нет в `DB_EXTRA_TARGETS`, и накат упадёт вместо
   тихой миграции прода.
2. ~~**`set shell := ["bash", "-cu"]` в justfile.** Флаг `-u` превращает незаданный
   `$TEST_DATABASE_URL` в жёсткую ошибку вместо пустой подстановки.~~
   **[Ревизия §12: инвариант потерял объект.]** После перевода `db-test-migrate` на
   `{{test_db_local}}` подстановки `$TEST_DATABASE_URL` в рецепте нет, защищать `-u` здесь
   больше нечего. Пункт сохранён как исторический: флаг из justfile не убирать — он
   защищает другие рецепты, — но с этим инвариантом он больше не связан.
   Инвариант 1 (`override=False`) остаётся в силе: рецепт по-прежнему подаёт `DATABASE_URL`
   через process env поверх `backend/.env` с иным содержимым, и регрессионный тест (AC-7)
   не трогать.

### Что поглощается, а что нет

`conftest` в ревизии `7edca85` держит три рубежа перед `DROP SCHEMA`:

| Рубеж | Судьба |
|---|---|
| (a) равенство prod/test через `Settings().DATABASE_URL` | **поглощается** нормализованным сравнением: оно закрывает и дырку строкового равенства полных DSN (цели, различающиеся только query-параметрами) |
| (b) имя целевой БД обязано оканчиваться на `_test` | **остаётся отдельным рубежом.** Allowlist поглотить его не может принципиально: `udp_dev` — легитимная цель для миграций и приложения, то есть она **в** списке, но `DROP SCHEMA` на ней катастрофа. Членство в allowlist выражает «можно мутировать», а не «можно разрушить схему» — это разные права. Сохраняется с комментарием, чтобы исполнитель не снёс его по букве «остаётся один» |
| (c) грант `ALLOW_NEON_WRITES` при `is_neon_url(test_url)` | **исчезает.** Разрешение приходит из конфига (`DB_EXTRA_TARGETS` в `backend/.env`), а не из рантайм-мутации process env. **[Ревизия §12:** после исключения Neon test-ветки разрешение не нужно вообще — тестовая цель loopback**]** |

## 6. Тесты и герметичность

### Герметичность — обязательное AC

После правки коммита 1 `env_file` — абсолютный путь к `backend/.env`, значит unit-тесты
guard'а **детерминированно** читают реальный `.env` разработчика при любом CWD. А §9
предписывает разработчику вписать туда Neon test-ветку в `DB_EXTRA_TARGETS`. Без пина тесты
«дефолт пустой» и «битая запись — ошибка старта» будут зелёными в CI (файла нет) и красными
у каждого, кто выполнил инструкцию из этой же спеки. Это в точности мина, из-за которой
ломался `test_get_settings`, но гарантированная, а не случайная.

**AC:** autouse-фикстура в обоих тест-файлах guard'а пинит через `monkeypatch.setenv` **и**
`APP_ENV`, **и** `DB_EXTRA_TARGETS=""`. Механизм тот же, что делает пин работающим: process
env бьёт `env_file`.

### Состав

- **Чистый модуль** — нормализация (порт по умолчанию, query-параметры, регистр хоста,
  IPv6-литерал, битый DSN, пустой hostname), решение по `APP_ENV`, разбор
  `DB_EXTRA_TARGETS`, отсутствие креденшелов в тексте ошибки.
- **Обвязка** — переносится из `7edca85` по структуре: тесты проверяют, что guard **вызван**
  и вызван до открытия сессии; от оси не зависят. Меняются фикстуры и литерал в
  source-check. Приём «проверено мутацией» (удаление вызова роняет тест) сохраняется.
- **Регрессионный** — `override=False` в `env.py`, проверка по исходнику (прецедент такого
  теста уже есть — проверка порядка guard/`engine_from_config`).
- **Рубеж `_test`-суффикса** — тест плюс комментарий «не поглощается allowlist'ом».

### CI

(`.../postgres` и `.../udp_test`). Третьего значения enum не вводим — CI работает как `dev`.

## 7. Деплойный контракт

**Единственный источник обязательных переменных — таблица в `README.md`.** Она дополняется
`APP_ENV`. Здесь — только дельта, которую вводит эта спека:

| Переменная | Что знать при деплое |
|---|---|
| `APP_ENV=prod` | **Fail-closed только для не-loopback целей.** Забытый `APP_ENV` при Neon или докерном хосте `db` роняет процесс на старте с инструкцией в две строки. При `DATABASE_URL` на `localhost` (bare-metal on-prem) забытый `APP_ENV` **ничего не роняет** — процесс молча живёт как dev. Сегодня это эквивалентно, потому что `APP_ENV` не гейтит ничего кроме guard'а; см. инвариант единственного потребителя в §5 |
| `DB_EXTRA_TARGETS` | в prod **не нужен** — цели не проверяются. Только для дев-машин |
| `COOKIE_SECURE=True` | при HTTPS. Напоминание: в `.env.example` это уже комментарием, в деплойном контексте стоит повторить |

Профили — рецепты эксплуатации, не сущности в коде:

- **хостинг в компании:** `LLM_PROVIDER=gateway` + `GATEWAY_*` (фаза 2), `APP_ENV=prod`,
  `DATABASE_URL` на локальный или докерный Postgres;
- **сторонний хостинг:** `LLM_PROVIDER=openrouter` + `OPENROUTER_API_KEY`, `APP_ENV=prod`,
  `DATABASE_URL` — Neon или иное.

## 10. Критерии приёмки

- **AC-0** (коммит 1, предусловие). `Settings.model_config.env_file` — абсолютный путь
  (`Path(__file__).parent / ".env"`); роутер настроек собирает `Settings(_env_file=ENV_PATH)`;
  пин `OPENROUTER_MODEL=""`, добавленный в `a8601aa`, снят, и `test_get_settings` зелёный без
  него. Формально это частичная отмена `a8601aa`: пин лечил симптом при незакрытом корне,
  корень закрывается — пин уходит.
- **AC-1.** `APP_ENV` — `Literal["dev","prod"]`, дефолт `dev`. Невалидное значение падает на
  валидации `Settings`.
- **AC-2.** При `APP_ENV=dev` мутация не-loopback цели, отсутствующей в `DB_EXTRA_TARGETS`,
  прерывается `RuntimeError` до сетевого коннекта — на всех трёх call-site.
- **AC-3.** При `APP_ENV=prod` цели не проверяются.
- **AC-4.** Сравнение по нормализованной тройке `host:port/dbname`; query-параметры
  отбрасываются; пустой hostname запрещён и отображается как `<нераспознанный хост>`.
- **AC-5.** Текст ошибки содержит цель в формате, копируемом в `DB_EXTRA_TARGETS` без
  редактирования, называет оба выхода и не содержит креденшелов.
- **AC-6.** Autouse-фикстура в обоих тест-файлах guard'а пинит `APP_ENV` и
  `DB_EXTRA_TARGETS=""` через `monkeypatch.setenv`. Тесты зелёные и при наличии, и при
  отсутствии `backend/.env` с непустым `DB_EXTRA_TARGETS`.
- **AC-7.** Регрессионный тест фиксирует `override=False` у `load_dotenv` в `alembic/env.py`.
- **AC-8.** Рубеж «имя целевой БД оканчивается на `_test`» сохранён, покрыт тестом и
  комментарием о непоглощаемости.
- **AC-9.** Снятие условия `!= "mistral-ocr"` и смена дефолта на `native` — **одно
  неделимое изменение**. Порознь они друг друга ломают: условие глушит warning для случая
  «легаси равно код-дефолту», поэтому после смены дефолта на `native` оно начнёт глушить
  `PDF_ENGINE=native` из легаси-`.env`.
- **AC-10.** `ALLOW_NEON_WRITES` и `is_neon_url` отсутствуют в коде и живой документации:

  ```bash
  git grep -l "ALLOW_NEON_WRITES\|is_neon_url" -- ':!docs/superpowers' ':!docs/devlog'
  ```

  даёт пустой вывод. **Архивные деревья `docs/superpowers` и `docs/devlog` исключены
  намеренно:** §3 этой спеки и будущий девлог хранят историю решений, и именно она не даёт
  отклонённой оси всплыть заново. Вычищать их — уничтожать ту самую запись, ради которой §3
  существует. Проверено: без исключений `git grep` находит и саму спеку.
- **AC-11.** `just lint` чист, `just test` зелёный, `just db-test-check` без дрейфа. Счётчик
  пропущенных тестов в CI не вырос относительно baseline — иначе новые `pytest.skip`
  проглотили интеграционный слой, и зелёный CI ничего не доказывает.
  **Baseline — зелёный прогон CI `backend-tests` на `7edca85`** (run 30288104267):
  `645 passed, 6 skipped`. Число устойчиво, а не случайно: все 6 пропусков — из
  параметризации `tests/test_auth_coverage.py` («публичный endpoint — auth не требуется»),
  то есть структурные, не зависящие от окружения прогона. Если baseline на момент старта
  работ отличается — зафиксировать актуальное значение из зелёного прогона и сверять с ним.
- **AC-12.** `main` вендорную ось не видит: рефактор влит в `feat/local-dev-db` до мержа PR #45.

## 11. Что не входит

- Переименование `CONFIDENCE_THRESHOLD`, `ALLOWED_ORIGINS`, `TRUSTED_PROXIES` — требует
  миграции существующих `.env`, вынесено в TECH_DEBT.
- Файлы-пресеты — отложены до фазы 2 (§3).
- Реализация `LLM_PROVIDER=gateway` — фаза 2, ждёт Keycloak-спайка.
- Docker-артефакты: в репозитории их нет вовсе, докерный вариант БД сейчас существует только
  как деплойный сценарий, а не как код.

## 12. Ревизия 2026-07-28: Neon test-ветка исключена

**Решение владельца.** Neon test-ветка не нужна. Она будет существовать только при
реализации плана и только если развёртывание пойдёт на сторонний хост (профиль 2 §7). Тесты
идут на локальном кластере, версии которого совпадают с Neon точно (16.14, `vector`,
`pg_trgm`).

Фиксируется **поверх** §5, §6 и §9, а не переписыванием их: разделы содержат рассуждение,
которое привело к решению, и его сохранение — та же причина, по которой существует таблица
отклонённых вариантов §3. Отменённые места помечены ссылками на эту секцию.

**Следствия:**

| Что | Было | Стало |
|---|---|---|
| MANUAL-шаг §9 | предусловие коммита 2, стоп с запросом у человека | **отменён.** `DB_EXTRA_TARGETS` пуст, окно не открывается |
| Замена потребителя `db-test-migrate` §5 | цель Neon test-ветки в `DB_EXTRA_TARGETS` | рецепт целится в `{{test_db_local}}` (loopback), разрешение не нужно |
| «Осознанное ужесточение» §6 | разработчик вносит ветку в список | **отменено.** Осталось другое ужесточение: локальный кластер обязателен для прогона тестов |
| Инвариант `-u` §5 | защищает подстановку `$TEST_DATABASE_URL` в рецепте | **потерял объект** — подстановки нет. Флаг из justfile не убирать, но с этим инвариантом он не связан |
| Инвариант `override=False` §5 | защищает process-env над `backend/.env` | **в силе**, регрессионный тест AC-7 не трогать |
| `DB_EXTRA_TARGETS` | обслуживает Neon test-ветку | **остаётся с нулём потребителей** — обоснование в §5, оно не Rule of Two |

**Что уходит из тестовой инфраструктуры** (реализуется задачей 8 плана):

- `TEST_DATABASE_URL` в `.env.test.example` — на локальный `udp_test` вместо Neon-DSN;
- fallback в `test-backend` свёрнут: рецепт становится алиасом `test-backend-local`.
  Маршрутизация отказа обязана идти через зависимость `pg-test-start`, а **не** через
  коннект: если просто нацелить `TEST_DATABASE_URL` на `localhost:5459/udp_test`,
  контрибьютор без кластера получит psycopg-traceback на `DROP SCHEMA` (все три
  `pytest.skip` в `db_engine` проходят раньше первого коннекта, а `create_engine` ленив),
  вместо внятного «не установлен — см. docs/testing.md»;
- `db-test-migrate` — на `{{test_db_local}}`, как уже сделано в `db-test-check`. Сейчас
  рецепт читает `$TEST_DATABASE_URL` из шелла (в justfile нет `dotenv-load`), то есть требует
  ручного экспорта, которого после ухода ветки никто делать не будет;
- кавеат «все пути в Neon недоступны» в `docs/testing.md` — становится неактуальным;
- `docs/setup/neon-setup.md` **остаётся**: он обслуживает живой профиль «сторонний хостинг»
  §7. Проверено — раздела про создание test-ветки в нём нет, помечать нечего.

**Цена, которую принимаем:** локальный кластер становится обязательным для прогона тестов на
дев-машине. Контрибьютора без кластера обслуживает CI (`uv run pytest` напрямую, не через
`just` — свёртка алиаса CI не задевает).
