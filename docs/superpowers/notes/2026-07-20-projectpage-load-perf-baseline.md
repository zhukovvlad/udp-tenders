# ProjectPage load perf — замер, точка 1 (baseline, до PR-1)

**Дата:** 2026-07-20. **Окружение:** dev-Neon (`ep-twilight-term-...eu-central-1`), read-only.
**Метод:** прямой замер `compute_calculations` (доминирующая работа внутри `/summary`) + `EXPLAIN (ANALYZE, BUFFERS)` на двух горячих помесячных запросах, которые целят новые индексы. HTTP-обвязка `/summary` (auth + сериализация + пара агрегатных запросов) добавляет фиксированный оверхед поверх этого ядра; замерено именно оптимизируемое ядро — оно воспроизводимо во всех трёх точках без auth-дэнса. Harness: `scratchpad/baseline_measure.py`.

## Форма набора (dev-Neon, единственный проект с данными)

| project | docs | invoices | items | months | диапазон |
|---|---|---|---|---|---|
| id=1 | 109 | 105 | 410 | 16 | 2023-12 .. 2025-03 |

`excluded_supplier_ids`: пусто. `calc_rows` на выходе: 40.

## Тайминг `compute_calculations` (N=25, полный период)

| min | p50 | p95 | max | mean |
|---|---|---|---|---|
| 2795 ms | **2888 ms** | **3108 ms** | 4246 ms | 2964 ms |

## EXPLAIN (ANALYZE, BUFFERS) — первый месяц (5 инвойсов)

- **invoice_ids_month** (`invoices ⋈ documents`, фильтр project_id + date): Hash Join, **Execution Time 0.072 ms**. Seq Scan на `documents` (109 строк) и `invoices` (105). Buffers: shared hit=5.
- **base_rows** (`invoice_items` по `invoice_id = ANY(...)` + item_type): GroupAggregate → Seq Scan, **Execution Time 0.129 ms**. Rows Removed by Filter: 404 из 410. Buffers: shared hit=16.

## Вывод

Время `/summary` — **round-trip-bound, не query-bound**: ~80 последовательных SQL (≈5/месяц × 16 месяцев) × ~37 ms RTT до Neon ≈ 2.9 s. Исполнение каждого запроса — 0.07–0.13 ms (таблицы малы → Seq Scan мгновенный).

- **PR-1 (индексы)** на этих данных **эффекта не даст** — EXPLAIN доказывает: доминирует не исполнение запроса, а сеть. Индексы — страховка на масштаб (ставка подтверждена, не измеримый выигрыш сейчас). Честно зафиксировано в теле миграции и TECH_DEBT.
- **PR-2 (устранение второго `compute_calculations` + round-trip)** — реальный выигрыш: сейчас расчёт идёт дважды (в `/summary`, затем в `/calculations`), устранение второго прогона снимает ~2.9 s на пути calc-данных.

## Ограничения замера

- Данные малы (1 проект, 105 инвойсов) — цифры ориентировочны; выводов об эффекте индексов **на масштабе** отсюда не делаем (нужен нагрузочный набор перед решением о вариантах B/C).
- Замерено ядро `compute_calculations`, не полный HTTP `/summary`; для точек 2/3 использовать тот же harness на том же проекте (id=1) для сопоставимости.

**Следующие точки:** точка 3 — после PR-2 (ожидаем ~0 повторных вызовов `/calculations` + сокращение time-to-ready).

# Точка 2 — после PR-1 (индексы на dev-Neon)

**Дата:** 2026-07-20. Индексы `ix_documents_project_id`, `ix_invoices_document_id_date` применены на dev-Neon (миграция `6e3b8dc47ba9`, подтверждены в `pg_indexes`). Тот же harness, тот же проект id=1.

## Тайминг `compute_calculations` (N=25)

| min | p50 | p95 | max | mean |
|---|---|---|---|---|
| 2854 ms | **2934 ms** | **3158 ms** | 4430 ms | 3019 ms |

Против baseline (p50=2888/p95=3108) — **статистически без изменений** (разница в пределах шума RTT).

## EXPLAIN — первый месяц

- **invoice_ids_month**: по-прежнему **Seq Scan** на `documents` и `invoices`, Execution Time 0.073 ms. Планировщик НЕ использует новые индексы — при 105 инвойсах / 109 документах seq scan дешевле index scan (индексы существуют, но не выбираются на таком объёме).

## Вывод точки 2

Ставка на масштаб подтверждена эмпирически: PR-1 не даёт (и по замыслу не должен давать) выигрыша на текущих малых данных — планировщик корректно игнорирует индексы, регрессии нет. Реальный выигрыш ожидается от PR-2 (устранение второго `compute_calculations`), не от индексов. Эффект индексов измерим только на нагрузочном наборе (гейт варианта B/C).

## Открытый вопрос к проверке на масштабе (ревью Codex P2 / Fable Minor)

`ix_documents_project_id` частично перекрывается левым префиксом уникального индекса `uq_documents_project_file_hash (project_id, file_hash)` — его префикс `(project_id)` тоже обслуживает `WHERE project_id = ?`. Оставлен осознанно (спека §3.2, самый частый фильтр, узкий B-tree плотнее композита, documents — low-write). **На точке 3 / нагрузочном наборе** снять `EXPLAIN` по скану `documents` за `project_id`: если планировщик стабильно предпочитает `uq`-индекс, `ix_documents_project_id` — кандидат на снос. `ix_invoices_document_id_date` в этом вопросе не участвует (обоснован однозначно).
