# Масштабирование: добавление новых типов материалов

Как добавить тип материала (пример — `mortar` «Раствор», ревизия `216a3d19213d`) и что при этом происходит автоматически.

---

## Текущая архитектура

- **`material_types`** — справочник: `code`, `name` (русская подпись), `default_unit_id` (ожидаемая размерность объёма/эталонов).
- **`material_classes`** — `(material_type_id FK, name)`, уникальны по паре (`uq_material_classes_type_name`); имя канонизируется `normalize_class_name` (`crud/materials.py`, см. `docs/agent/database.md`).

| `code` | Подпись | Примеры класса | Ед. |
|---|---|---|---|
| `concrete` | Бетон | `В25`, `В7.5`, «Цементное молоко» | м³ |
| `rebar` | Арматура | `А500С`, `А240`, «Проволока вязальная» | т |
| `mortar` | Раствор | `М200`, `М150` | м³ |
| `other` | Прочее | «Кирпич М150», «Газоблок D500» (материал + марка) | — |

---

## Что работает автоматически при новом типе

- **API / CRUD / расчёты** — всё по `material_class_id` / `material_type_id`, без списков кодов.
- **Направления** — каждый тип, кроме `other`, становится направлением дашборда и экспорта (`routers/dashboard.py`); направление без данных в проекте скрыто. Объём считается в `default_unit` типа.
- **Фронт** — подписи и варианты выбора типа берутся из `GET /api/material-types` (`useMaterialTypeLabels`, `frontend/src/lib/materialTypes.ts`); «Прочее» в списках последним.
- **Парсинг** — фаза B резолвит `material_type` из ответа модели по справочнику; неизвестный код → `other` с warning.

## Чеклист: добавление нового типа

- [ ] **Ревизия Alembic** (`just db-revision "add <type> material type"`): `INSERT INTO material_types … ON CONFLICT (code) DO NOTHING` с `default_unit_id`. `MATERIAL_TYPES_SEED` в `crud/units.py` НЕ дополнять — это снимок, который импортирует историческая ревизия `e1f2a3b4c5d6`.
- [ ] **Перенос накопленных классов** (если материал уже копился в `other`) — data-миграция по признаку в `raw_name`, с переносом только классов, у которых ВСЕ позиции подходят; одноимённый класс в новом типе → слияние (образец — `move_mortar_classes` в `216a3d19213d`). Откат — с отказом при конфликте имён.
- [ ] **Промпт** (`SYSTEM_PROMPT` в `pdf_parser.py`): ветка в правиле `material_type`, формат `material_class` для типа (короткая марка/класс, без полной спецификации), место в правиле `calc_role="base"`.
- [ ] **Фикстура и тест разбора**: сценарий в `tests/fixtures/openrouter/` + интеграционный тест «upload → класс нужного типа» (образец — `mortar.json`, `test_upload_mortar_and_other_material_classes`).
- [ ] **Тесты набора типов**: `test_material_types_seeded`, `test_list_material_types`; фронтовая фикстура `sampleMaterialTypes`.
- [ ] Прод: миграция — `APP_ENV=prod just db_target=env db-migrate`.

## Потенциальное будущее

Если типов станет много (5+) или их захочется настраивать без деплоя, правила промпта можно генерировать из справочника (поле-подсказка `class_hint` в `material_types`). Сейчас преждевременно: правила типа в промпте пишутся вручную вместе с ревизией.
