# 2026-10-15 — Тип материала «Раствор» и правило «материал + марка»

**Ветка:** `feat/mortar-material-type`
**PR:** [#51](https://github.com/zhukovvlad/udp-tenders/pull/51)
**Метод:** разбор позиций класса в `udp_dev` → выбор варианта с владельцем → TDD

## Задача

Класс `М200` сидел в типе «Прочее». Предположение «это бетон М200 ≈ В15» не подтвердилось: все
4 позиции — строительный раствор («Раствор М200Пк3F50», «Цементный раствор М200 ПК3 F100»), и
модель сделала ровно то, что велел промпт (раствор → `other`). Реальная проблема — голая марка в
«Прочем»: кирпич М200 слился бы с раствором в один класс, одну историю цен и один коридор.
Решение владельца: отдельный тип «Раствор» + правило «материал + марка» для «Прочего».

## Что сделано

1. **Ревизия `216a3d19213d`**: тип `mortar` «Раствор» (`default_unit` — м³) через
   `INSERT … ON CONFLICT (code) DO NOTHING`; `move_mortar_classes` переносит из `other` классы, у
   которых **все** позиции — раствор; одноимённый класс в `mortar` → слияние (позиции, эталоны,
   коридоры; коридор-дубль проекта удаляется с warning). Откат
   (`restore_other`) возвращает классы в «Прочее», удаляет тип-уровневые коридоры и тип; при
   одноимённом классе в «Прочем» — `RuntimeError` с просьбой слить вручную.
2. **Промпт** (`pdf_parser.py`): раствор (кладочный, штукатурный, цементный, цементно-песчаный) →
   `material_type="mortar"`, класс — только марка (`М200`, без `Пк3 F50`); base-материал «Прочего» —
   «материал + марка/характеристика» с заглавной (`Кирпич М150`, `Газоблок D500`), голая марка
   запрещена.
3. **Фронт**: подписи типов были захардкожены в трёх местах (`Materials.tsx`, `MaterialPage.tsx`,
   `CorridorsTab.tsx`). Новый хук `useMaterialTypeLabels()` (`lib/materialTypes.ts`) берёт подписи и
   опции селекта из `/api/material-types` (`material_types.name`), «Прочее» последним — следующий
   тип появится в UI без правки фронта. Удалена неподключённая страница `MaterialClasses.tsx`.
4. **Документация**: `docs/scaling-material-types.md` переписан под текущую схему (справочник
   `material_types`, уникальность классов, подписи с сервера, направления, чеклист добавления типа);
   `docs/agent/database.md` — `mortar` и правило имени класса.

5. **Ревью-раунд** (Codex ×2, владелец):
   - Признак `ILIKE '%раствор%'` ловил «Растворитель 646», «Растворонасос» и «Добавку для раствора» —
     класс растворителя целиком уехал бы в «Раствор» с единицей м³. Теперь позиция — раствор, только
     если наименование начинается со слова «раствор» (`\M` — конец слова), перед которым одни
     прилагательные (`~* '^\s*(прилагательное\s+)*раствор\M'`); неоднозначное остаётся в `other`.
   - Класс без своего коридора наследовал правило типа `other`, а `resolve_corridor` идёт
     «класс → тип → нет правила»: после смены типа класс молча стал бы некомпенсируемым. Перед
     переносом правило типа `other` закрепляется на классе в проектах, где класс используется
     (позиции или эталоны); своё правило класса не трогается.

## Решения и нюансы

- `MATERIAL_TYPES_SEED` (`crud/units.py`) **не дополнен**: его импортирует историческая ревизия
  `e1f2a3b4c5d6` при upgrade — дописать туда тип значило бы задним числом изменить её поведение на
  чистой БД (и сломать новую ревизию дублем). Рядом — комментарий-предупреждение.
- Любой тип, кроме `other`, автоматически становится направлением дашборда/экспорта (ADR #9);
  направление без данных в проекте скрыто — пустой «Раствор» в проектах без раствора не появится.
- Руководство `docs/scaling-material-types.md` нашлось уже после реализации; по нему добавлен
  пропущенный пункт — фикстура ответа модели и сквозной тест разбора нового типа.
- Характеристики сверх марки в класс не входят (как W/F у бетона): раствор F50 и F100 одной марки —
  один класс.
